# VibeCrates 추천 서버 개발 과정

2026년 5월부터 11월까지 VibeCrates AI 추천 서버를 만든 과정을 정리한 문서다. 작업 중 남긴 세션 보고서와 실험 기록을 요약했다. 서버가 어떻게 동작하는지는 [README](../README_KR.md)에 있고, 이 문서는 무엇을 왜 바꿨는지와 그 결과를 다룬다.

수치의 정의는 마지막 절 [지표 정의](#지표-정의)에 있다.

## 2. 주요 문제와 해결

### 2-1. 한국어 학습 쿼리에 영어가 섞였다 → 영어로 전환 (6월)

- **문제:** Qwen2.5-VL-7B로 한국어 학습 쿼리를 생성하자 영화 쿼리 42,295건 중 15.8%에 영어가 섞이고 9.0%는 형식이 깨졌다. 50건 재검증에서 영어 혼입은 영화 28%, 음악 22%, 책 20%였다.
- **원인:** 원본 데이터(줄거리, 블러브, 곡 정보)가 모두 영어라, 7B 모델이 영어 입력을 읽으면서 한국어 출력을 유지하지 못했다.
- **해결:** 학습 쿼리와 작품 텍스트를 모두 영어로 바꾸고 전체를 다시 생성했다. 한국어 검색어는 서빙 단계에서 처리하기로 했다(2-7).
- **모델 선정:** 같은 시기에 쿼리 생성 모델을 비교했다. PaliGemma 2 28B는 형식이 불안정했다. Qwen2.5-VL-32B(4-bit)는 건당 8.7초에 형식 유효율이 0%였다. 72B는 A100 40GB에서 메모리가 부족했다. 7B는 건당 1.2초, 형식 유효율 90~100%라 채택했다.

### 2-2. 음악의 텍스트 입력이 다른 도메인과 달랐다 → 세 도메인 분위기 설명 합성 (7~8월)

- **문제:** 영화와 책은 텍스트 입력이 3인칭 설명인데, 음악은 가사 원문을 500자 잘라 넣고 있었다. 40,036곡 중 가사만 있는 곡이 24,231곡(약 60%)이었고, 둘 다 없는 곡이 3,686곡(9.2%)이었다. 오디오 피처(energy, valence 등)는 전처리 함수만 있고 어디서도 쓰이지 않았다.
- **해결:** 세 도메인 모두 LLM이 원본 정보로 같은 형식의 분위기 설명을 합성하게 했다. 음악은 오디오 피처를 "차분한", "강렬한" 같은 서술구로 바꿔 넣었다. 40,036곡 전부가 오디오 프로필을 얻었고(곡당 평균 5.9개 서술구), 텍스트가 없던 3,686곡도 설명을 얻었다.
- **입력과 라벨 정렬:** 학습 쿼리를 만들 때 쓴 정보와 모델 입력 텍스트의 범위를 맞췄다(줄거리 600자, 감독·배우 제외). 모델이 입력에 없는 정보로 쿼리를 맞히도록 학습되는 것을 막기 위해서다.

### 2-3. 생성 작업이 느리고 중간에 멈췄다 → vLLM 배치, 입력 길이 방어 (8월)

- **처리량:** HuggingFace `generate`를 배치 1로 돌리면 영화 200건에 4분 55초가 걸렸고, GPU 메모리는 32GB 중 16.8GB만 썼다. vLLM 연속 배치로 바꾸자 512건이 22초에 끝났다. 34배 빨라져 전체 28만 회 생성이 116시간에서 4~5시간으로 줄었다.
- **중단:** 생성 파이프라인 네 단계가 같은 예외로 죽은 채 25시간 동안 방치됐다. 원인은 표지 이미지 토큰이었다. 1650×1650 표지 한 장이 입력 토큰 3,503개를 차지해 컨텍스트 한도 4,096을 넘었다. 실행 스크립트가 단계별 종료 코드를 확인하지 않아, 로그에는 마지막에 완료 표시가 찍혀 있었다.
- **해결:** 이미지 크기 상한을 두고, 단계마다 종료 코드를 확인하게 했다. 오염된 책 쿼리 캐시 23,147건은 버리고 다시 만들었다. 학습 전에 합성 결과를 검사하는 QA 도구(`scripts/synth/qa_synth_outputs.py`)를 만들었다.
- **표지 확보율:** 영화 포스터는 Amazon URL이 만료돼 404가 오는데도 9바이트짜리 파일이 생기고 있었다. TMDB에서 다시 받아 71.8% → 99.3%로 올렸다. 음악 표지는 Deezer에서 보강해 67.4% → 92.4%로 올렸다.

### 2-4. 검색에 쓰는 벡터가 학습되지 않고 있었다 → Stage 2 손실 교체 (8월)

- **문제:** Stage 2의 검증 손실이 15에폭 내내 0.000313 → 0.000310으로 평평했다.
- **원인:** 검색에 쓰는 작품 벡터 `z_content`는 ContentBlock의 출력인데, Stage 1의 손실 세 쌍에는 `z_content`가 없다. ContentBlock을 학습하는 유일한 손실인 Stage 2의 KL 증류가 배치 안의 작품 후보가 아니라 768개 임베딩 차원에 대한 분포를 맞추고 있었다. L2 정규화된 768차원 벡터의 성분은 ±0.036 정도라 softmax가 거의 균등해지고 기울기가 사라진다. 무관한 두 벡터의 KL(0.00128)과 실제 검증 손실(0.00031)이 같은 자릿수였다.
- **해결:** Stage 2 손실을 배치 안 후보에 대한 InfoNCE로 바꿨다. 검증 손실이 4.16에서 0.24로 실제로 내려갔고, 작품 간 평균 코사인이 0.4375 → 0.0682로 퍼졌다(검색어 벡터의 0.0139에 가까워짐).

### 2-5. 고정했다고 생각한 CLIP이 학습되고 있었다 → 동결 버그 수정 (8월)

- **문제:** CLIP 인코더는 고정하도록 설계했는데, Stage 1 시작 시 트레이너가 이름에 `mlp`가 들어간 파라미터를 학습 대상으로 열었다. CLIP 트랜스포머의 각 층에도 `mlp`라는 서브모듈이 있어서 인코더 내부 2억 5,800만 개 파라미터가 19만 건 데이터로 전부 미세조정되고 있었다. SBERT는 내부 층 이름이 달라 영향이 없었다.
- **해결:** 헤드 MLP와 인코더 내부를 경로로 구분해, 학습 파라미터를 261,921,536개에서 5,575,936개로 줄였다. 학습 시작 시 블록별 학습 파라미터 수를 출력해 같은 실수를 바로 알아볼 수 있게 했다.
- **결과:** 판정 점수가 0.667 → 0.754로 올랐다(4.5 SE). 가장 크게 오른 것은 "우주를 배경으로 한 액션 영화"처럼 구체적인 검색어로, 0.610 → 0.875였다. CLIP이 원래 잘하던 영역의 지식이 미세조정으로 지워지고 있었다는 근거다.

**모델 개선 누적 결과**

6월 기준선 0.698에서 0.754가 됐다. 6월과 같은 검색어만 비교하면 0.698 → 0.847이다. 성능을 올린 것은 새 기법보다 이 두 구현 결함(2-4, 2-5)을 고친 것이었다.

### 2-6. 평가 지표를 믿을 수 없었다 → 판정기 수리, 쌍대 비교, 사람 검증 (8~10월)

검색 품질을 재는 방법 자체를 네 번 고쳤다.

1. **실행 간 비교 불가:** 6월 지표는 모델이 자기 임베딩으로 계산한 코사인이라, 학습이 바뀌면 공간이 달라져 실행끼리 비교할 수 없었다. 같은 LLM 판정기로 블라인드 재채점하는 방식으로 바꿨다.
2. **제목 편향:** 판정기가 작품 제목과 검색어의 단어 겹침에 끌렸다. 판정기에 보여 주는 텍스트에서 제목 문자열을 모두 지웠다. 작품 텍스트에 제목이 남는 비율이 98.9% → 0.7%로 줄었다.
3. **절대 점수의 한계:** 판정기와 사람의 등급 완전일치는 42.5%였다. 절대 등급 대신 두 모델 결과를 나란히 보여 주고 고르게 하는 쌍대 비교(`scripts/eval/judge_pairwise.py`)를 도입했다. 좌우를 바꿔 두 번 묻고 승률과 p값을 낸다. 이 방식으로 미결 실험 6건을 재학습 없이 닫았다.
4. **사람 라벨로 판정기 검증:**
   - 어휘 단서가 없는 쌍에서 판정기는 사람과 92.6% 일치했다.
   - 검색어와 단어만 겹치는 오답이 들어간 쌍 29개에서는 54.5%만 일치해 합격선 75%에 못 미쳤다. Gemma 3 27B로 바꾸거나 프롬프트를 바꿔도 나아지지 않았다.
   - 그래서 단어 겹침과 관련된 실험은 사람이 직접 평가하기로 했다.

### 2-7. 한국어 검색이 동작하지 않았다 → 번역 체인 (8~10월)

- **발견:** 판정 평가 1,600건이 모두 영어라 한국어 검색을 한 번도 재지 않았다. 같은 뜻의 한국어·영어 검색어 40쌍을 비교했다.
  - 두 검색어 벡터의 코사인이 0.058로, 거의 직교했다.
  - 두 검색 결과의 상위 10개는 40쌍 모두 하나도 겹치지 않았다.
- **원인:** CLIP 텍스트 인코더는 영어 BPE 토크나이저를 쓴다. "비 오는 오후의 조용한 시간"이 의미 없는 바이트 조각 27개로 쪼개졌다.
- **해결 1 (8월):** 한글 검색어를 opus-mt-ko-en으로 번역한 뒤 인코딩했다. 한국어·영어 결과의 상위 10개 겹침이 0% → 29%가 됐다. 같은 뜻의 영어 문장끼리도 겹침이 평균 44%라는 점을 기준으로 함께 쟀다.
- **해결 2 (10월):** 백엔드 로그의 실제 검색어는 "로파이 비 오는 날"처럼 단어를 조합한 짧은 형태가 대부분이었다. 장르·분위기·상황 어휘 사전을 만들어 먼저 적용했고, 로그 530종에서 핵심어가 빠지는 비율이 33.0% → 0.0%가 됐다.
- **해결 3 (10월):** 문장형 검색어는 Gemma 3 4B로 번역한다. 1.5B는 품질이 부족했고, 27B는 약간 낫지만 무거웠다. 학교 GPU 서버에서 문장당 0.13초가 걸리고, 1초 안에 응답이 없으면 opus-mt로 넘어간다.
- **채택하지 않은 대안:** 다국어 인코더로 재학습하는 안은 착수하지 않았다. 번역만으로 영어 성능의 95%(0.730 대 0.766)가 나왔고, 재학습에는 설명 19만 건과 쿼리 9만 건의 재합성이 필요했다.

### 2-8. 한 도메인이 결과를 독차지했다 → 검색 시점 상한 (9월)

- **문제:** 도메인을 지정하지 않은 검색에서 한 도메인이 상위 10개를 모두 차지한 경우가 40개 중 12개(30%)였다.
- **학습으로 고치기:** 도메인 균형 배치와 필드명 통일로 재학습해 봤다. 품질은 해치지 않았지만 쏠림도 줄지 않았다. 원문과 임베딩 모두 필드 이름과 무관하게 98% 이상 도메인이 구분됐고, 남은 단서는 어휘와 문체 자체였다.
- **채택한 해결:** 검색 시점에 "도메인별 상위 5개까지, 단 검색어가 도메인을 지목하면 상한 없음" 규칙을 두고 백엔드에 넘겼다. 쏠림이 절반 아래로 줄었고 판정 점수 손해는 없었다. 지목 예외가 필요한 이유도 쟀다. 상한을 무조건 걸면 "우주 배경 액션 영화" 같은 검색어에서 쌍대 승률이 17.6%(p=0.0002)로 떨어졌다.
- **domain 필드:** 응답에 `domain` 필드를 추가해 검색어가 지목한 도메인을 백엔드에 알려 준다. 작품 종류 명사(영화·노래·소설 등)만 단서로 쓰고, 장르와 동사는 쓰지 않는다.

### 2-9. 서버가 조용히 실패했다 → 실패를 드러내는 구조 (8~10월)

- **가짜 벡터:** 모델 없이 띄운 개발용 서버가 12일간 검색어를 시드로 한 난수 벡터를 백엔드에 보내고 있었다. 응답에 `model_version`을 넣고, 작품 벡터 번들과 같은 체크포인트인지 대조하게 했다.
- **삼켜진 예외:** 서버 기동 중 인덱스 적재가 실패하면 예외를 로그 한 줄로 삼키고 추천만 503을 냈다. 원인은 parquet 엔진(pyarrow)이 없는 것이었고, 평가가 3일 멈춘 것도 같은 원인이었다. 기동 시 실패한 항목과 이유를 `/health`의 `errors`에 싣게 했다.
- **검색 위치 결정:** 검색은 백엔드의 벡터 DB(Qdrant)가 하고, 추천 서버는 검색어 벡터만 만든다. 작품 벡터는 CSV 번들로 넘긴다. 번들에는 표지가 있는 작품만 넣었다(183,165개).
- **서버 이전:** 노트북 서버는 잠자기와 메모리 부족으로 꺼졌다. 학교 GPU 서버(A100)로 옮겨 API 서버와 번역 서버를 함께 돌린다. 이전 뒤 같은 검색어의 벡터가 이전 서버와 일치하는지(코사인 1.000000) 확인했다. 서버 내부 처리 시간은 검색어당 11ms다.

### 2-10. 부정 표현을 읽지 못한다 → 측정 후 보류 (10월)

- **측정:** "판타지 소설 / 무서운 판타지 소설 / 무섭지 않은 판타지 소설" 형태의 116세트로 쟀다. 기본형에서 특성형으로 가는 방향을 1로 놓았을 때, 부정형은 그 방향으로 중앙값 +0.63만큼 움직였다. 116세트 모두 특성 쪽으로 움직였다. 모델이 "무섭지 않은"을 "무서운"처럼 읽는다는 뜻이다.
- **원인:** 학습 전 CLIP 출력이 이미 +0.78이었다. 고정된 CLIP 텍스트 인코더의 한계이고, 학습은 이 값을 조금 줄였다. 번역은 원인이 아니었다. 부정 검색어 100개에서 Gemma는 82개를 맞게 옮겼다(opus-mt는 27개).
- **관련 연구 검토:** NegBench(Alhamoud et al., "Vision-Language Models Do Not Understand Negation", CVPR 2025)를 읽고 우리 구조에 적용할 수 있는지 검토했다.
  - 이 논문은 이미지·영상·의료 데이터 79k 예제로 CLIP 계열 모델이 부정을 무시하고 긍정 문장처럼 처리한다는 것을 보였다. 우리 측정과 같은 현상이다.
  - CC12M 이미지에 LLaMA 3.1로 부정 표현이 들어간 캡션을 합성한 데이터(CC12M-NegCap, CC12M-NegMCQ)로 CLIP을 파인튜닝했다.
  - COCO에서 CLIP을 NegCap으로 학습하면 부정 검색어의 R-Neg@5가 48.0% → 57.8%(+9.8%p)로 올랐다. NegCLIP을 NegCap과 NegMCQ를 합친 NegFull로 학습하면 부정 캡션 객관식 정확도가 28.6% → 56.2%(+27.6%p)로 올랐다.
  - 한계도 함께 확인했다. CLIP을 NegFull로 학습하면 일반 검색 R@5가 COCO 54.8% → 54.2%, MSR-VTT 50.6% → 46.9%로 떨어졌다. 학습 데이터가 일반 이미지 캡션이라 분위기 검색어와 분포도 다르다.
- **보류:** 서비스 로그의 한국어 검색어 약 4만 종에서 특성을 부정하는 검색은 사실상 없었다. 관련 연구(NegBench, NevIR)도 부정 데이터 학습으로 일부만 개선했다. 실제 사용자 로그에 부정 검색이 나타나면 번역 단계에서 반대말로 바꾸기, 백엔드 필터 같은 비용이 낮은 방법부터 적용한다.

## 4. 남은 한계와 다음 단계

- **실제 사용자 데이터 부족:** 지금까지의 평가는 LLM이 만든 검색어와 판정에 기대고 있다. 백엔드에 행동 로그(검색, 추천 노출, 좋아요, 보드 수정, 상세 보기) 요구사항을 넘겼고, 이 로그가 쌓이면 실제 검색어 분포로 평가와 학습 데이터를 다시 만든다.
- **부정 표현 파인튜닝:** NegBench의 부정 캡션 데이터(CC12M-NegCap)로 CLIP 텍스트 인코더(Query Block)를 파인튜닝한다. 고정했던 인코더를 여는 것이라 두 가지를 함께 확인한다.
  - **기존 성능 유지:** 2-5에서 본 것처럼 인코더를 학습하면 사전학습 지식이 지워질 수 있고, NegBench에서도 일반 검색 성능이 떨어진 설정이 있었다. 일반 검색어에서 쌍대 비교로 손해가 없는지 확인한다.
  - **부정 개선 측정:** 2-10의 116세트로 이동 비율(+0.63)이 실제로 줄어드는지 잰다. 예전에 학습한 CLIP LoRA 체크포인트도 +0.59로 거의 같았지만, 그때는 부정 데이터 없이 학습한 것이라 조건이 다르다.
- **은유적 검색어 번역:** 은유적인 검색어는 번역문의 뜻이 원문과 어긋나는 경우가 있다.
- **어휘 겹침 평가:** 단어만 겹치는 오답을 LLM 판정기가 가려내지 못하므로, 이 축의 실험은 사람 라벨로만 평가할 수 있다.

## 지표 정의

- **판정 점수:** LLM 판정기(Qwen2.5-VL-7B)가 (검색어, 추천 작품) 쌍마다 매긴 관련성 등급(관련 있음 / 애매 / 관련 없음)의 평균이다. 절대값은 판정기에 따라 달라지므로, 같은 판정기로 잰 실행 간 차이만 비교한다.
- **SE (표준오차):** 평균이 표본에 따라 흔들리는 폭. 두 실행의 차이가 2 SE 이상이면 유의, 1 SE 미만이면 노이즈로 본다.
- **쌍대 승률:** 두 모델의 결과를 나란히 보여 주고 판정기가 고른 비율이다. 50%면 차이 없음이고, p값은 그 차이가 우연일 확률이다.
- **코사인 유사도:** 두 벡터가 이루는 각도의 코사인. 1이면 같은 방향, 0이면 직교다.
- **상위 10개 겹침:** 두 검색 결과의 상위 10개 중 같은 작품의 비율이다.
- **InfoNCE:** 대조 학습 손실. 같은 배치의 다른 항목을 오답으로 삼아 정답과의 유사도를 상대적으로 높인다.
